## 2026-08-25 — Production CSRF bug, phone/DOB validation, address checkbox, banner visibility

Written retroactively — this session's build-log entry was missed at the time; logging it now before the next session's changes land on top, since the commit (`730298f`) already shipped these four fixes.

- **Root cause of the "something went wrong" bug a parent hit in production**: found via real Cloud Run logs (`gcloud run services logs read`), not guessed — repeated `POST 403` on `/api/admissions/inquiries/`. Reproduced deterministically with a local Django test client: an *authenticated* session got `403 CSRF cookie not set`, an anonymous one got the correct `400`. Root cause: DRF's default `SessionAuthentication` only enforces CSRF when `request.user` is authenticated — which happens whenever the same browser also has a logged-in `/admin/` session (cookies are domain-wide), exactly what the logs showed (an admin login, then browsing, then testing `/inquiry` in the same browser). All 4 DRF views in this project are `AllowAny` with no legitimate authenticated-API use case, so the fix was global: `REST_FRAMEWORK["DEFAULT_AUTHENTICATION_CLASSES"] = []` in `settings.py`
- Guardian 2's "same address as above" pattern reused for a new "same address as guardian 1" checkbox on the student's address (frontend-only value copy, same as the existing guardian-2 checkbox — no new server-side flag needed)
- Phone format (`+233XXXXXXXXX`, country code + 9 digits) validated both client-side (immediate inline error) and server-side (`RegexValidator` on `InquiryGuardianSerializer.phone`, automatically covering both Inquiry and Application since they share that serializer)
- Date of birth switched from the browser's locale-dependent native `<input type="date">` to a masked dd/mm/yyyy text input, converted to ISO only when building the API payload — the only way to guarantee a consistent display format across browsers, since native date inputs can't be forced into a specific display format
- Error/success banner now scrolls into view on submit (`scrollIntoView`) — it sat at the top of a long form, invisible without scrolling up after submitting from the bottom
- All four fixes applied to `index.html`, `application.html`, and (banner visibility only) `offer.html`, mirrored into the deployed `backend/templates/public/` copies
- Verified with a real Playwright run against the local dev server for all four fixes, and the CSRF fix specifically re-verified with the same authenticated-session repro afterward, confirming it now behaves like the anonymous case

### 1. Cloudflare Turnstile + rate limiting

Added to the three public action endpoints (Inquiry, Application's final submit, Offer accept/decline) — not the draft save/autosave endpoints, which don't create anything a bot benefits from and would make a multi-minute form re-solve a challenge on every autosave.

- `TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY` default to Cloudflare's own published "always passes" test keys — not disabled/empty, so local dev exercises the real Cloudflare round trip. Confirmed both directions actually hit Cloudflare for real: the "always fails" test secret key correctly triggered a rejection through `verify_turnstile_token()`, and the "always fails" test *sitekey* correctly made the widget itself refuse to produce a token client-side, which the frontend's pre-submit check caught with zero API calls fired.

- **Two real bugs found only by testing this, not by reading Cloudflare's docs:**
  1. The widget container had a `cf-turnstile` class (seemed harmless/conventional) — that class makes Cloudflare's script auto-scan and implicitly render the widget before the app's own explicit `turnstile.render()` call runs, which silently loses that race (console warning: "already exists in this container"). The implicit render never wires up the custom `callback`, so the JS-side token variable stayed empty forever even though the widget visibly worked and its hidden `cf-turnstile-response` input *did* get populated — invisible unless the actual JS variable is checked, not just "does a token appear somewhere." Fixed by dropping the class from all three widget containers.
  2. On `application.html`, rendering the widget eagerly at page load (inside the initially-hidden Declaration step) would have meant Cloudflare's iframe sizing itself against a `display:none` container. Rendered lazily instead — only the first time the Declaration step actually becomes visible.
- Rate limiting: the code-side half (Django's existing `AnonRateThrottle`/`DraftRateThrottle`) was already in place from the earlier free-navigation fix — this session added the *other* half, a Cloudflare-side rate-limit rule on `/api/admissions/*`, which is dashboard config, not code (Cloudflare needs to see the traffic before Cloud Run does, which Django-side throttling can't do). ### 4. Submission latency + draft-save-after-submit bug

Investigated with real evidence on both, per the explicit instruction not to guess:

**Latency** — `gcloud logging read` on the real Cloud Run service showed the actual submit endpoint taking 3.6s on a warm instance (no cold start nearby), and separately showed plain draft-save requests occasionally spiking to 5-6s — turned out to be Cloud Run cold starts (`min-instances=0`), confirmed by a "Starting new instance... AUTOSCALING" log line at the exact same timestamp, not an email slowdown. Directly measured `django.core.mail.get_connection().open()` against the real Resend relay: ~2.5-3s per connection, every time — and `emails.py`'s `_send()` opened a brand-new one for *every* email, with a submission sending two (guardian confirmation + staff alert) sequentially. That's the confirmed root cause, not a frontend bug — the fetch/response-handling code was already correct.

Fixed with `_shared_connection()` in `emails.py`, a context manager opening **one** SMTP connection reused across both `_send()` calls per submission event, falling back to independent per-email connections (existing behavior) if even the shared connection can't be opened — keeps the "email plumbing never blocks the real submission" guarantee. Verified the improvement directly: a 2-rejected-email test case (real Resend sandbox rejections — `example.com` recipients, an unverified sending domain — both slower than a real send) dropped from 13.6s to 10.2s, a ~3.4s reduction matching almost exactly one avoided connection-open.

This doesn't eliminate the latency, just roughly halves the connection-setup portion of it — the response still waits on Resend synchronously. True fire-and-forget dispatch would need an actual task queue (Cloud Tasks or similar), since Cloud Run only guarantees CPU during an active request by default; flagged as a real option in `02-stack-and-schema.md` and `03-build-order.md` rather than built, since it's new GCP infrastructure with its own cost, not a code-only fix. Also added a frontend reassurance: "Still submitting — this can take up to 15 seconds…" replaces the bare "Submitting…" after 4 seconds, so a genuinely multi-second wait doesn't read as stuck.

**Draft-save failure** — reproduced by checking real production logs, not the first (successful) local repro attempt: two `400`s on `PATCH .../application-drafts/<token>/` for a token that had already been successfully submitted 4-5 minutes earlier. Root cause: the free-navigation success handler only ever disabled `nextBtn`/`submitBtn`/`backBtn` — the sidebar nav and "Save & finish later" button stayed clickable after a successful submit, and clicking either autosaves via `saveDraft()`, which PATCHes the now-submitted draft and gets a real, correctly-behaving `400 "This application has already been submitted"` — surfaced as a confusing generic "Could not save your progress" error. Very plausibly the same parent from the latency bug above, unsure the slow submit had worked and clicking around afterward.

Fixed with `lockFormAsSubmitted()` (disables the whole form — nav, both step buttons, save-later — not just three of them), called on a successful submit. As defense in depth for a case the client-side lock can't cover (e.g. a stale second tab left open after submitting from another one), `saveDraft()` now also recognizes an `"already been submitted"` 400 specifically and treats it as success rather than a failure. Confirmed end-to-end with a real full 6-step submission through a real headless browser: reassurance text appeared after 4s, submission succeeded, the submit button changed to "Application submitted," and forced clicks on the (now-disabled) sidebar and save-later button afterward correctly produced zero API calls and zero navigation.

All test data (Families, Applications, Documents in Supabase Storage) created during this session's testing cleaned up afterward.

**New admin action — `retry_failed_recipients`:** after the fix above, the first live test campaign (id 4, `delivered@resend.dev` + real personal addresses) ended up `status="failed"` with all 11 recipients failed — one `@example.com` address in the batch made Resend reject the whole all-or-nothing batch call. Added `EmailCampaignAdmin.retry_failed_recipients`, gated on `can_send_bulk_email` same as Send: it only resets rows currently `status="failed"` back to `pending` and re-enqueues them via the existing `enqueue_campaign_send` — it never touches `sent` rows or recomputes the recipient list from Guardians, preserving the pending-only re-query idempotency guarantee everywhere else in this system. ## 2026-08-28 — Fix the batch-collateral-damage bug, deploy everything from this incident

The user deliberately reproduced the underlying bug behind the campaign-4 failure: set 2 of 7 test recipients to `@example.com`, sent the campaign, and confirmed all 7 — not just the 2 bad ones — were marked `failed`, since Resend's batch API is genuinely all-or-nothing (matches what was already documented, now confirmed a second time independently). `retry_failed_recipients` recovers from this after the fact, but the user asked for a real fix at the source: validate addresses before they're ever batched, so one bad address can't take a whole batch of otherwise-good ones down with it.

**Where it fits, and why:** validation happens in `bulk_email.enqueue_campaign_send`, immediately before pending recipients are grouped into batches — not at campaign creation. A campaign can sit as a draft for a while before Send, so Guardian data can change in between; more importantly, `enqueue_campaign_send` is the one function every path that queues a send (`send_campaign`, `retry_failed_recipients`) already funnels through, so this is the single choke point that guarantees a bad address can never reach Resend regardless of which action queued it.

**What shipped:** `bulk_email.invalid_email_reason()` — Django's own `EmailValidator` for basic format, plus a small explicit blocklist of placeholder domains (`example.com`/`.org`/`.net`/`.edu`, `test.com`) justified directly by Resend's own rejection message ("domains like `example.com`"), not guessed. Explicitly scoped as a defense against obviously-malformed/placeholder addresses, not a deliverability guarantee — a valid-looking address at a dead domain still bounces after sending, which needs bounce-webhook handling and stays out of scope, same as documented in `02-stack-and-schema.md`. New `skipped_invalid` recipient status and `EmailCampaign.skipped_count` field (migration `0013`). Rejected rows are marked immediately and never see a Cloud Task. Deduplicated the "recompute counts, finalize if nothing's left pending" logic — previously only in `BulkEmailBatchSendView._finalize_if_done` — into `bulk_email.finalize_campaign()`, since `enqueue_campaign_send` now also needs it for the case where *every* pending recipient turns out invalid (no Cloud Task ever gets created to finalize it otherwise). `retry_failed_recipients` extended to also pick up `skipped_invalid` rows alongside `failed` ones, same safety properties as before.

**Testing:** a real campaign with 4 valid (`delivered@resend.dev`) recipients and 1 deliberately malformed address in the same batch — the malformed one was flagged `skipped_invalid` before any Resend call; the 4 valid ones sent successfully with real Resend message ids. This is the actual regression fix, confirmed directly: the batch no longer fails as a whole. First run of this test used the not-yet-deployed code locally for enqueueing, so `BulkEmailBatchSendView`'s finalize step ran on the *old* deployed revision and correctly didn't know about `skipped_count` (it stayed `0` even though the recipient row itself was correctly `skipped_invalid`) — verified this was purely a deploy-lag artifact via an isolated unit test of `finalize_campaign()` with no network involved (sent=1/failed=0/skipped=1, correct), then re-ran the same mixed-batch test after deploying and got `skipped=1` end-to-end for real, confirming the fix runs correctly inside the actual deployed service, not just locally.
