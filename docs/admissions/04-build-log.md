## 2026-08-18 — Phase 3: Decisions, offers, waitlist/capacity tracking, gated enrollment
- Plan proposed and reviewed before building in two passes: the first covering the Decision/Offer/Capacity shape and the `can_decide` permission (confirming no role/permission infrastructure existed anywhere in code — verified directly, not assumed), the second incorporating offer expiry (14 days, lazily resolved — no scheduler exists in this project), sharing the offer-stage and enrolled-stage gates through one mechanism, and adding `waitlisted`/`rejected`/`offer_declined` as real stage values
- `Decision`, `Offer`, `Capacity` models; `Application.save()` gained a shared `GATED_STAGES` mechanism blocking entry to `offer` (needs accepted Decision) and `enrolled` (needs accepted Decision + accepted Offer) — enforced in the model itself, not just an admin action, so every entry point is covered
- Negative outcomes (waitlisted/rejected Decision, declined/expired Offer) auto-propagate onto `Application.stage`; positive outcomes never auto-advance, only unlock the next gate for a deliberate staff action — this asymmetry was the actual answer to "does an expired offer roll the stage back automatically" from the planning discussion
- `admissions.can_decide` — a plain Django Group/Permission (`Meta.permissions` on `Decision`), gating the `DecisionInline`/`OfferInline` and the `generate_offer`/`reset_offer` admin actions via `get_actions()`, which Django's own action dispatch treats as a real functional block, not just a hidden UI option
- Real bug found and fixed during testing: `Decision.save()`/`Offer.save()`'s stage-propagation logic trusted `self.application.stage`, which can be a stale, already-mutated-in-memory value when triggered from inside `Application.save()`'s own gate check (exactly what `_bulk_set_stage` does — mutates `.stage` before calling `.save()`). The expiry test caught this; the decline test happened not to exercise the path. Fixed by always re-fetching the `Application` row fresh instead of trusting a possibly-cached instance
- Tested via Django's real admin test client, a real HTTP POST to the token endpoint, and a real headless-browser pass on `offer.html`: the full positive chain (Decision→Offer→parent accepts→enrolls, `student_id` assigned), the decline chain (auto-rolls to `offer_declined`, enrollment blocked), the expiry chain (lazy detection flips the offer and rolls the stage, same block), the `can_decide` permission in both directions, entering `offer` with zero Decision (correctly raises), and `waitlisted` propagation
- Not built despite being in the original Phase 3 plan: the soft capacity-warning check — `Capacity` is storage only, nothing reads it yet (caught during the next session's documentation audit, not before)
- Not tested: waitlist promotion specifically (waitlisted → accepted → Generate Offer) — the code path looks correct by inspection but wasn't exercised
- Commit: `a11115f` "Phase 3: Decisions, offers, waitlist/capacity tracking, and gated enrollment."
