## 2026-08-25 — Production CSRF bug, phone/DOB validation, address checkbox, banner visibility

Written retroactively — this session's build-log entry was missed at the time; logging it now before the next session's changes land on top, since the commit (`730298f`) already shipped these four fixes.

- **Root cause of the "something went wrong" bug a parent hit in production**: found via real Cloud Run logs (`gcloud run services logs read`), not guessed — repeated `POST 403` on `/api/admissions/inquiries/`. Reproduced deterministically with a local Django test client: an *authenticated* session got `403 CSRF cookie not set`, an anonymous one got the correct `400`. Root cause: DRF's default `SessionAuthentication` only enforces CSRF when `request.user` is authenticated — which happens whenever the same browser also has a logged-in `/admin/` session (cookies are domain-wide), exactly what the logs showed (an admin login, then browsing, then testing `/inquiry` in the same browser). All 4 DRF views in this project are `AllowAny` with no legitimate authenticated-API use case, so the fix was global: `REST_FRAMEWORK["DEFAULT_AUTHENTICATION_CLASSES"] = []` in `settings.py`
- Guardian 2's "same address as above" pattern reused for a new "same address as guardian 1" checkbox on the student's address (frontend-only value copy, same as the existing guardian-2 checkbox — no new server-side flag needed)
- Phone format (`+233XXXXXXXXX`, country code + 9 digits) validated both client-side (immediate inline error) and server-side (`RegexValidator` on `InquiryGuardianSerializer.phone`, automatically covering both Inquiry and Application since they share that serializer)
- Date of birth switched from the browser's locale-dependent native `<input type="date">` to a masked dd/mm/yyyy text input, converted to ISO only when building the API payload — the only way to guarantee a consistent display format across browsers, since native date inputs can't be forced into a specific display format
- Error/success banner now scrolls into view on submit (`scrollIntoView`) — it sat at the top of a long form, invisible without scrolling up after submitting from the bottom
- All four fixes applied to `index.html`, `application.html`, and (banner visibility only) `offer.html`, mirrored into the deployed `backend/templates/public/` copies
- Verified with a real Playwright run against the local dev server for all four fixes, and the CSRF fix specifically re-verified with the same authenticated-session repro afterward, confirming it now behaves like the anonymous case

## 2026-08-26 — Phase 5 follow-up: free section navigation

Replaced the 6-step form's strictly linear Next/Back with free jump-between-sections — a sidebar (desktop) / horizontal scrollable bar (mobile) listing all 6 sections, clickable in any order, no mid-form validation blocking (consistent with the draft/resume system's whole premise: fill what you have, come back for the rest).

- `application.html` restructured into a `.layout` flex row: the `<form>` on the left, a new `<nav id="section-nav">` (6 buttons, one per step) on the right — `position: sticky` on desktop, collapsing via a `@media (max-width: 860px)` query into a horizontal `overflow-x: auto` strip pinned above the form (`order: -1`) rather than a second, separate mobile-only markup structure
- `isStepComplete(n)` replaces the old blocking `validateCurrentStepRequiredFields()` — checks required-field presence for *any* step (not just the current one), driving a checkmark/empty-dot per sidebar item, recomputed on every `input`/`change` across the whole form. Deliberately checks `el.hidden` directly rather than `el.offsetParent === null` for "is this field currently required" — `offsetParent` reads `null` for every field inside *any* non-visible step's container too, which would have made every non-current step's fields silently skip validation and falsely report "complete"
- `goToStep(n)` is now the single entry point for all navigation (sidebar clicks, Next, Back) — autosaves in both directions, not just forward, satisfying "autosave on every section change"
- Final submit now checks `isStepComplete` for all 6 steps first; if any are incomplete, shows a summary naming each one with a clickable link (`goToStep`) instead of a generic error, and — new — server-side 400s are also mapped from error key to step (`stepForErrorKey`) and jump the parent to the first affected section automatically
- **A real bug found while testing, not before**: the shared `AnonRateThrottle` (20/hour, previously fine for infrequent one-shot submissions) started producing background `429`s during testing, because free navigation autosaves far more often than the old fixed 5-click linear flow ever did. Worse, `saveDraft()` never checked the response status — `fetch()` doesn't reject on a non-2xx response, only on a network failure — so a throttled or failed autosave was reported as a success with nothing shown to the parent, meaning a real user who jumped between sections enough times could lose progress silently. Fixed both sides: a dedicated `DraftRateThrottle` (`application_draft` scope, 120/hour) applied only to the create/save-progress draft endpoints — not the actual submission endpoints, which keep the tight default rate as an anti-abuse measure — and `saveDraft()`/`ensureDraftToken()` now return `true`/`false` so every caller (section navigation, "save for later", final submit) can surface a visible warning on failure instead of assuming success
- **A second bug found while testing the mobile layout**: the sidebar's desktop-only `flex: 0 0 210px` (fixing its *width* in the row-direction desktop layout) was never reset inside the mobile media query — since `.layout` becomes `flex-direction: column` on mobile, that same rule fixed the nav's *height* at 210px instead, rendering it as six huge stacked boxes instead of a compact horizontal strip. Caught from an actual mobile-viewport screenshot, not just a code read; fixed by adding `flex: 0 0 auto` to the mobile override
- Tested end to end: jumping to Declaration and Student directly, skipping Guardian entirely (no block); a step marked incomplete on the sidebar with only one of several required fields filled, then correctly complete after finishing it; data preserved when navigating away and back; autosave firing on sidebar clicks (not just Next); the incomplete-section summary at submit correctly naming exactly the unfinished sections and excluding finished ones; a full submission completed by deliberately filling every section out of order (Emergency → Guardian → Declaration → Student → Health → Documents), landing correctly in the database; the mobile layout (column stacking, horizontal scroll, tap-to-jump) confirmed via real viewport screenshots before and after the height-bug fix
- All test data cleaned up afterward

## 2026-08-26 — Document upload constraints: type/size allow-list

Application form document uploads (`proof_of_vaccination`, `financial_clearance`, `previous_report`, `application_fee_proof`) previously had no type or size restriction anywhere — any file, any size, would mint a signed URL and upload successfully.

- Allowed types: PDF, JPG/JPEG, PNG (`admissions/storage.py:ALLOWED_UPLOAD_EXTENSIONS`/`EXTENSION_MIME_TYPES`). HEIC (default iPhone photo format) considered and deliberately excluded — Safari renders it, most other browsers don't, so a staff member reviewing documents in admin could hit an unviewable file; flagged to the user as a tradeoff rather than decided silently
- Max size: new `MAX_UPLOAD_SIZE_MB` setting, default 10MB
- Enforced at three layers, in increasing order of trust: the browser (`handleFileSelected` in `application.html`, checks extension + `file.size` before calling `/upload-url/` — instant feedback, trivially bypassed), `UploadURLRequestSerializer` (new `file_size` field, rejects a bad extension or oversized declared size with a clean 400 before a signed URL is minted — still trusts the client-declared size), and the Supabase bucket itself (`file_size_limit`/`allowed_mime_types`, set via new `manage.py configure_storage_bucket` → `storage.configure_bucket_limits()`) — the only layer that checks the real bytes/Content-Type on the actual `PUT`, confirmed via research that Supabase Storage enforces bucket config regardless of upload method (signed URL or otherwise)
- Ran `configure_storage_bucket` against the real production Supabase bucket (this project's only Supabase instance — local dev already points at it, there's no separate storage emulator)
- Tested for real against the live bucket, not just read the API docs: requested a signed URL declaring a small `file_size` then actually PUT an 11MB file — got a real `413 EntityTooLarge` back from Supabase; PUT with `Content-Type: application/x-msdownload` — got a real `415 InvalidMimeType`; confirmed a legitimate small PDF still uploads successfully (both via direct `curl` and via a real headless-browser run through `/apply`, including the client-side rejection messages rendering correctly for both the disallowed-type and oversized cases). All test objects deleted from the bucket afterward, except one small stray 62-byte test file from an earlier run in this session whose exact storage path wasn't captured before cleanup — low-value orphan, noted here rather than silently left unmentioned
- New `docs/deployment.md` step 5b: run `configure_storage_bucket` as a Cloud Run Job (same pattern as the migrations job), and re-run it any time `MAX_UPLOAD_SIZE_MB` or the allowed extensions change — not automatic, not part of the regular deploy
